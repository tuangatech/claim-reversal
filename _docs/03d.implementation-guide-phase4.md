## Goal

Wire up the full end-to-end pipeline: a custom `AppealCrew` orchestrator runs direct tool calls (Intake, Physician, Submission), delegates to a CrewAI Writer Agent (autonomous draft→validate→retry loop), and communicates with the remote Clinical Evidence Agent via A2A. SSE events stream to the browser in real time. The HITL pause at evidence insufficiency surfaces through the UI, and a human resume decision continues or closes the workflow.

After Phase 4:
- Submitting a claim ID in the browser runs the full pipeline with real LLM reasoning
- SSE events update the timeline in real time as each step completes
- The Writer agent autonomously drafts, validates, and retries the appeal letter
- The HITL decision card appears when evidence is insufficient (CLM-2026-00199)
- Clicking Proceed/Close in the UI resumes the suspended workflow
- HITL timeout auto-closes after `HITL_TIMEOUT_SECONDS`
- Killing the evidence agent triggers graceful degradation (no crash)
- All events are written to the `appeal_events` audit log via MCP
- The `appeals` table tracks state progression

**Estimated time:** 6–8 hours

## Architecture Reminder

```
Browser → POST /appeal → main.py spawns run_crew() as asyncio task
                         ↓
           run_crew() uses AppealCrew — NOT CrewAI's Crew.kickoff()
                         ↓
           AppealCrew orchestrator:
             1. Run intake tool directly → DenialRecord (rules-based)
             2. Call A2A evidence agent via httpx → EvidenceBundle (or HITL pause)
             3. Delegate to CrewAI Writer Agent → AppealLetter (LLM reasoning loop)
             4. Run physician tool directly → PhysicianReview (rules-based)
             5. Run submission tool directly → SubmissionConfirmation (rules-based)
                         ↓
           Each step emits WorkflowEvent to the claim's asyncio.Queue
                         ↓
Browser ← GET /stream/{id} reads from that queue via SSE
```

**Why not use `Crew.kickoff()`?** Three hard constraints prevent it:
1. **HITL async pause** — The pipeline must suspend mid-execution (after evidence), wait for an HTTP POST from the browser, then resume. CrewAI tasks run to completion; there's no built-in way to park a crew on an `asyncio.Event`.
2. **Early termination** — If intake says "close" (non-clinical, deadline passed, low score), downstream tasks must be skipped. CrewAI sequential crews execute all tasks in order without conditional skipping.
3. **SSE substep granularity** — The UI needs 34 fine-grained events (`intake_parsing`, `intake_classifying`, etc.). CrewAI's `step_callback` fires per tool call, not at custom substep boundaries you control.

**Why use a CrewAI Agent for the Writer?** A CrewAI agent's value is deciding which tool to call, with what arguments, and how to interpret the result — not just executing a fixed sequence. The Writer must compose text, evaluate quality, interpret validation feedback, and decide whether to retry. That's genuine reasoning. The other steps (Intake, Physician, Submission) are deterministic — code lookups, date arithmetic, score formulas — and gain nothing from an LLM reasoning loop.

### Step 4.1 — Rewrite `crew/appeal_crew.py` as a Manual Pipeline

**File:** `crew/appeal_crew.py`

**Purpose:** Replaces the stub orchestrator with a fully functional async pipeline that runs each workflow step sequentially, manages A2A delegation to the evidence agent, delegates to the CrewAI Writer agent, handles HITL suspension, and emits SSE events.

**Class: `AppealCrew`**

```python
class AppealCrew:
    def __init__(self, claim_id: str, event_queue: asyncio.Queue):
        ...

    async def run(self) -> None:
        ...
```

**Constructor parameters:**
- `claim_id: str` — the claim being processed
- `event_queue: asyncio.Queue` — the SSE queue for this claim (events put here appear in the browser)

**Constructor initialises:**
- Stores `claim_id` and `event_queue`
- Creates `httpx.AsyncClient` for A2A calls (base URL from env: `http://localhost:{EVIDENCE_AGENT_PORT}`)
- Creates `self.mcp_client: McpClient` — shared MCP client instance from `shared/mcp_client.py` (connects to :8002 via SSE)
- Creates `self.hitl_event: asyncio.Event` — used to pause the pipeline waiting for human input
- Creates `self.hitl_choice: str | None = None` — stores the human's decision when resume fires
- Stores `self.a2a_task_id: str | None = None` — correlation key for A2A resume

**`async def run(self) -> None` — the pipeline:**

This is the main entrypoint called by `main.py`. Steps in order:

1. **Intake** — call `_run_intake()`. If recommendation is not "proceed", emit `CASE_CLOSED` and return.
2. **Evidence** — call `_run_evidence()`. If result is a closed signal, emit `CASE_CLOSED` and return.
3. **Writer** — call `_run_writer()`.
4. **Physician** — call `_run_physician()`.
5. **Submission** — call `_run_submission()`. Emit `APPEAL_SUBMITTED`.

Wrap the entire pipeline in try/except. On any exception, emit an `ERROR` event with the exception message.

**Private methods:**

#### `async def _run_intake(self) -> DenialRecord | None`

1. Read the EOB data from the DB (`appeals` table, `denial_record` column — already JSON).
2. Parse it into fields needed by `triage_denial()`.
3. Fetch claim history via MCP: `claim_history = await self.mcp_client.get_claim_history(claim_id)`.
4. Call `triage_denial(claim_id, denial_reason_code, claim_amount, payer_id, date_of_service, denial_date, claim_history=claim_history)` — sync tool, pass MCP data as parameter.
5. Call `await self.mcp_client.log_appeal_event(claim_id, "intake_complete", {...}, "intake")`.
6. Build a `DenialRecord` Pydantic model combining EOB data + triage results.
7. Update DB: `UPDATE appeals SET status = 'intake', denial_record = ? WHERE id = ?` (store the full DenialRecord JSON).
8. Emit SSE: `WorkflowStep.INTAKE_COMPLETE`, status `"success"`, message with recommendation and score.
9. If recommendation != "proceed", return `None`. Otherwise return the `DenialRecord`.

#### `async def _run_evidence(self) -> EvidenceBundle | None`

1. Emit SSE: `WorkflowStep.EVIDENCE_GATHERING`, status `"success"`, message "Gathering clinical evidence...".
2. Build A2A request payload from `self.denial_record`:
   ```json
   {
     "messages": [{"role": "user", "parts": [{"type": "data", "data": {
       "claim_id": "...",
       "diagnosis_codes": [...],
       "payer_id": "...",
       "denial_reason_code": "..."
     }}]}]
   }
   ```
3. POST to `http://localhost:{EVIDENCE_AGENT_PORT}/a2a` with timeout 120s.
4. **If request fails** (connection error, timeout): emit `ERROR` event with "Evidence agent unavailable" and return `None`. This is the `fail_fast=False` graceful degradation.
5. Parse response. Check `status.state`:
   - `"completed"`: Extract `evidence_bundle` or `closed_reason` from response data.
   - `"input-required"`: Store `task_id` from response `id` field. Enter HITL flow (see below).
6. **If completed with `evidence_bundle`**: Parse into `EvidenceBundle`, update DB (`evidence_bundle` column), emit `EVIDENCE_GATHERED`, return bundle.
7. **If completed with `closed_reason`**: Return `None` (caller emits `CASE_CLOSED`).

**HITL flow (when `status.state == "input-required"`):**

1. Store `self.a2a_task_id = response["id"]`.
2. Extract interrupt payload (sufficiency_reasoning, evidence_gathered, options) from response messages.
3. Emit SSE: `WorkflowStep.HUMAN_REVIEW_REQUIRED`, status `"waiting"`, payload includes the interrupt payload fields.
4. **Start timeout**: create an `asyncio.wait_for(self.hitl_event.wait(), timeout=HITL_TIMEOUT_SECONDS)`.
5. **If timeout fires**: set `self.hitl_choice = "close"`.
6. **If event is set** (human responded): `self.hitl_choice` was already set by `resume()`.
7. Emit SSE: `WorkflowStep.HITL_RESPONSE_RECEIVED`, message with the choice.
8. Build resume A2A request:
   ```json
   {
     "id": "<self.a2a_task_id>",
     "messages": [{"role": "user", "parts": [{"type": "data", "data": {
       "human_choice": "<self.hitl_choice>"
     }}]}]
   }
   ```
9. POST to A2A `/a2a` endpoint with the resume payload.
10. Parse response. If `evidence_bundle` present → build `EvidenceBundle`, emit `EVIDENCE_GATHERED_PARTIAL`, return bundle. If `closed_reason` → return `None`.

#### `async def _run_writer(self) -> AppealLetter`

This step delegates to a **CrewAI Agent** that owns the full draft→validate→retry loop autonomously.

1. Fetch payer rules via MCP: `payer_rules = await self.mcp_client.get_payer_appeal_rules(self.denial_record.payer_id)`.
2. Emit SSE substeps: `DRAFTING_PAYER_RULES`, `DRAFTING_RULES_LOADED`.
3. Create pre-bound tool closures (see Step 4.1b below) that capture `denial_record`, `evidence_bundle`, `payer_rules`, `event_queue`, and `self.mcp_client` (for `log_appeal_event` calls from inside tools).
4. Build the CrewAI Writer agent via `AppealWriterAgent` factory with those tools.
5. Create a CrewAI `Task` with description: "Draft a compelling appeal letter, validate it against the evidence, retry once if validation score < 0.7, then return the final letter as JSON."
6. Execute the task via `await asyncio.to_thread(agent.execute_task, task)` (CrewAI is sync).
7. Parse the agent's output (JSON string) into an `AppealLetter` Pydantic model.
8. Call `await self.mcp_client.log_appeal_event(claim_id, "letter_drafted", {...}, "writer")`.
9. Update DB: `appeal_letter` column.
10. Emit SSE: `WorkflowStep.LETTER_DRAFTED`, status `"success"`.
11. Return the `AppealLetter`.

**Fallback:** If the agent's output can't be parsed into `AppealLetter`, extract just the text from the output and construct the model manually (the agent might return the letter text without full JSON structure).

### Step 4.1b — CrewAI Writer Agent with Pre-Bound Tools

**File:** `agents/writer_agent.py`

**Purpose:** Factory that produces a configured CrewAI `Agent` with pre-bound tools. The orchestrator creates this agent at runtime with all the context already baked into the tool closures.

**Class: `AppealWriterAgent`**

```python
class AppealWriterAgent:
    def __init__(self, denial_record, evidence_bundle, payer_rules, event_queue):
        ...

    def build(self) -> Agent:
        """Returns a CrewAI Agent with pre-bound draft and validate tools."""
        ...
```

**Pre-bound tool closures:**

The orchestrator passes `denial_record`, `evidence_bundle`, `payer_rules`, and `event_queue` to the factory. The factory creates two CrewAI `@tool`-decorated functions that close over this context:

```python
from crewai import tool

@tool("draft_appeal_letter")
def draft_tool(validation_feedback: str = "") -> str:
    """Drafts a formal medical appeal letter. Pass validation_feedback if redrafting."""
    # emit SSE: DRAFTING_COMPOSING
    # calls draft_appeal_letter(denial_record, evidence_bundle, payer_rules, feedback)
    # returns AppealLetter as JSON string
    ...

@tool("validate_appeal_letter")
def validate_tool(letter_json: str) -> str:
    """Validates the drafted letter against evidence. Returns score and issues."""
    # emit SSE: LETTER_VALIDATING
    # calls validate_appeal_letter(letter, denial_record, evidence_bundle, payer_rules)
    # emit SSE: LETTER_VALIDATED with score
    # returns LetterValidationResult as JSON string
    ...
```

**Key design points:**
- Tools emit SSE events directly via the pre-bound `event_queue` reference. This gives mid-loop timeline detail without waiting for the agent to complete.
- Tools accept/return strings (CrewAI constraint). The orchestrator deserializes the final output.
- A shared mutable container (e.g., `result_holder = {"letter": None}`) is set by the draft tool — the orchestrator reads it after task execution to get the typed `AppealLetter` without relying on string parsing.
- The task description caps retries: "validate once, retry at most once if invalid, then return the best result."

**Agent definition:**

```python
return Agent(
    role="Appeal Writer",
    goal="Draft a compelling, evidence-backed appeal letter that passes validation",
    backstory="You are a skilled medical appeal writer...",
    tools=[draft_tool, validate_tool],
    llm=get_crewai_llm_string(),
    verbose=True,
    max_iter=6,  # safety cap: draft + validate + redraft + validate + return
)
```

#### `async def _run_physician(self) -> PhysicianReview`

1. Call `physician_review(claim_id, denial_type, claim_amount, payer_id, letter_text)` — sync local tool.
2. Call `await self.mcp_client.log_appeal_event(claim_id, "physician_reviewed", {...}, "physician")`.
3. Emit SSE: `WorkflowStep.PHYSICIAN_REVIEWED`, status `"success"`, message notes whether attestation was required.
4. Return the `PhysicianReview`.

#### `async def _run_submission(self) -> SubmissionConfirmation`

1. Fetch payer rules via MCP (if not already cached from writer step): `payer_rules = await self.mcp_client.get_payer_appeal_rules(payer_id)`.
2. Call `submit_appeal(claim_id, payer_id, letter_text, payer_rules=payer_rules)` — sync local tool, payer rules passed as parameter.
3. Call `await self.mcp_client.log_appeal_event(claim_id, "appeal_submitted", {...}, "submission")`.
4. Emit SSE: `WorkflowStep.APPEAL_SUBMITTED`, status `"success"`, message includes confirmation number.
5. Return the `SubmissionConfirmation`.

#### `def resume(self, choice: str) -> None`

Called by `main.py` when the human POSTs to `/appeal/{claim_id}/resume`. Sets `self.hitl_choice = choice` and calls `self.hitl_event.set()` to wake the paused pipeline.

**Helper: `async def _emit(self, step, status, message, payload=None)`**

Builds a `WorkflowEvent` and puts it on `self.event_queue`. Keeps the emit calls DRY.

### Step 4.2 — Rewrite `main.py` to Use the Real Crew

**File:** `main.py`

**Changes from the Phase 1 stub:**

1. **Replace `run_crew()` stub** with code that instantiates `AppealCrew` and calls `await crew.run()`.

2. **Add crew registry**: A module-level dict `active_crews: dict[str, AppealCrew] = {}` that maps `claim_id` to the running `AppealCrew` instance. Needed so the resume endpoint can call `crew.resume(choice)`.

3. **Update `POST /appeal`** — includes per-claim reset for re-runnability:
   ```python
   @app.post("/appeal")
   async def start_appeal(request: AppealRequest):
       # Validate claim exists
       conn = get_connection()
       row = conn.execute("SELECT id FROM appeals WHERE id = ?", (request.claim_id,)).fetchone()
       if not row:
           conn.close()
           raise HTTPException(status_code=404, detail=f"Claim {request.claim_id} not found")

       # Reset claim state for re-run (testing/demo — same claim can be submitted multiple times)
       conn.execute(
           "UPDATE appeals SET status='pending', evidence_bundle=NULL, appeal_letter=NULL, submission=NULL, updated_at=CURRENT_TIMESTAMP WHERE id=?",
           (request.claim_id,),
       )
       conn.execute("DELETE FROM appeal_events WHERE claim_id=?", (request.claim_id,))
       conn.commit()
       conn.close()

       # Create SSE queue and crew
       event_queues[request.claim_id] = asyncio.Queue()
       crew = AppealCrew(request.claim_id, event_queues[request.claim_id])
       active_crews[request.claim_id] = crew

       # Spawn the pipeline as a background task
       asyncio.create_task(_run_and_cleanup(request.claim_id, crew))
       return {"claim_id": request.claim_id, "status": "started"}
   ```

   **Why reset per-claim instead of resetting the whole DB?** We only have 2 test patients. During testing and demo, you'll submit the same claim ID repeatedly. Resetting that specific claim's state (back to `pending`, clearing outputs) lets you re-run without restarting services. The `appeal_events` for that claim are also cleared so the audit trail shows only the current run. Previous claims' data stays intact for comparison.

4. **Add `_run_and_cleanup` helper**:
   ```python
   async def _run_and_cleanup(claim_id: str, crew: AppealCrew) -> None:
       """Runs the crew and removes it from active_crews when done."""
       try:
           await crew.run()
       finally:
           active_crews.pop(claim_id, None)
   ```

5. **Implement `POST /appeal/{claim_id}/resume`**:
   ```python
   @app.post("/appeal/{claim_id}/resume")
   async def resume_appeal(claim_id: str, request: ResumeRequest):
       crew = active_crews.get(claim_id)
       if not crew:
           raise HTTPException(status_code=404, detail="No active workflow for this claim")
       if request.choice not in ("proceed", "close"):
           raise HTTPException(status_code=400, detail="Choice must be 'proceed' or 'close'")
       crew.resume(request.choice)
       return {"claim_id": claim_id, "choice": request.choice, "status": "resumed"}
   ```

6. **Update app title**: Change `FastAPI(title="Claim Denied"...)` to `FastAPI(title="Claim Reversal"...)`.

7. **Remove the old `run_crew()` stub function** entirely.

8. **Keep existing**: `GET /stream/{claim_id}`, `GET /health`, `emit_event()`, lifespan, CORS middleware.

## Verification Checklist

**Crew pipeline — happy path (CLM-2026-00123):**
- [ ] Full pipeline completes: Intake → Evidence → Writer → Physician → Submission
- [ ] No HITL pause triggered
- [ ] `appeals.status == "submitted"` in DB
- [ ] `evidence_bundle.partial == False`
- [ ] Appeal letter references clinical evidence and guideline citations
- [ ] Submission confirmation has a valid confirmation number

**Crew pipeline — HITL proceed (CLM-2026-00199):**
- [ ] Pipeline pauses at evidence gathering (HUMAN_REVIEW_REQUIRED SSE event emitted)
- [ ] Calling `crew.resume("proceed")` continues the pipeline
- [ ] `evidence_bundle.partial == True`
- [ ] Appeal letter notes that evidence is partial
- [ ] Full pipeline completes through submission

**Crew pipeline — HITL close (CLM-2026-00199):**
- [ ] Pipeline pauses at evidence gathering
- [ ] Calling `crew.resume("close")` terminates the pipeline
- [ ] CASE_CLOSED SSE event emitted
- [ ] No appeal letter generated
- [ ] DB status reflects closure

**HITL timeout:**
- [ ] Set `HITL_TIMEOUT_SECONDS=5`; submit CLM-2026-00199; don't click anything
- [ ] After ~5s, CASE_CLOSED event emitted with timeout message
- [ ] Pipeline terminates cleanly

**Graceful degradation:**
- [ ] Kill evidence agent (stop :8001 process)
- [ ] Submit CLM-2026-00123 in the browser
- [ ] ERROR event appears — no crash, no hanging

**SSE streaming:**

## Design Notes for the Implementer

**Why a custom orchestrator instead of `Crew.kickoff()`:**

CrewAI's `Crew.kickoff()` runs tasks sequentially and passes context between agents. Our pipeline has three requirements that `kickoff()` cannot handle:
1. **HITL async pause** — The pipeline must suspend mid-execution, wait for an HTTP POST, then resume. CrewAI tasks run to completion with no `asyncio.Event` suspension.
2. **Early termination** — If intake says "close", downstream tasks must be skipped. CrewAI sequential crews execute all tasks unconditionally.
3. **SSE substep granularity** — 34 fine-grained events at custom boundaries. CrewAI's `step_callback` fires per tool call, not at arbitrary substep points.

The orchestrator calls deterministic tools directly (Intake, Physician, Submission) and delegates to a CrewAI Agent only for the Writer, where LLM reasoning adds value.

**Why the Writer is a CrewAI Agent (not a direct tool call):**

The Writer's draft→validate→retry loop is genuine reasoning: the agent must decide whether the letter is good enough, interpret validation feedback, and compose a better draft. This is what CrewAI agents are designed for — autonomous tool-calling loops where the LLM decides what to do next. Wrapping this in direct orchestrator code (as we do for Intake/Physician/Submission) would work, but wouldn't demonstrate CrewAI's value.

**Pre-binding context into tool closures:**

CrewAI tools can only accept simple arguments (strings). Our tools need `DenialRecord`, `EvidenceBundle`, and `payer_rules`. The solution: the orchestrator creates tool closures at runtime with context already captured. The agent just calls `draft_appeal_letter()` and `validate_appeal_letter()` without passing complex objects — they're already baked in.

**SSE emission from inside CrewAI tools:**

Strict separation says "agents don't touch the SSE queue." But without it, the timeline shows nothing between "started writing" and "finished writing" (30+ seconds of silence). The pragmatic solution: tools emit SSE events via a pre-bound queue reference. This gives `drafting_composing`, `letter_validating`, `letter_validated` events mid-loop. The orchestrator still handles pre/post events (`drafting_payer_rules`, `letter_drafted`).

**A2A call is async, tool functions are sync:**

The local tools (`triage_denial`, `draft_appeal_letter`, etc.) are synchronous functions. The crew pipeline wraps them in `asyncio.to_thread()` or calls them directly since they're fast (mock data) or make blocking HTTP calls (LLM via OpenRouter). The A2A call uses `httpx.AsyncClient` natively.

For draft_appeal_letter (which calls OpenRouter synchronously via the `openai` SDK), wrap in `asyncio.to_thread()`:
```python
letter = await asyncio.to_thread(draft_appeal_letter, denial_record, evidence_bundle, payer_rules)
```

**HITL event coordination:**

The `asyncio.Event` pattern works because:
- The crew pipeline runs in a single asyncio task (`create_task`)
- It `await`s on `hitl_event.wait()` inside that task
- The `/appeal/{id}/resume` endpoint calls `crew.resume()` which sets the event
- Both run in the same event loop (FastAPI's)

**Database status progression:**

Update `appeals.status` at each step so the DB reflects progress even if the process crashes:
- After intake: `status = "intake"`
- After evidence: `status = "evidence"`
- After writer: `status = "drafting"`
- After physician: `status = "physician"`
- After submission: `status = "submitted"`
- On close: `status = "closed"`

**MCP tool calls — all via MCP client protocol:**

All MCP tool calls route through the MCP client (`shared/mcp_client.py`) over SSE transport to port 8002. The orchestrator holds an `McpClient` instance initialized in the constructor and calls MCP tools as async methods: `await self.mcp_client.get_claim_history(...)`, `await self.mcp_client.log_appeal_event(...)`, etc.

Local tools (`triage_denial`, `physician_review`, `submit_appeal`) remain pure sync functions. They receive MCP data as parameters from the orchestrator rather than fetching it themselves. This keeps them testable without a running MCP server.

The MCP server must be running before the main app starts. The `McpClient` includes connection retry with backoff to handle startup ordering.
